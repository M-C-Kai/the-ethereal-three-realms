## 附加块语义复核（2026-09-17，B 级证据）

消费方为 tooltip 构建器 `pmsj/work/e/b.smali`、人物装备页
`e/ag.smali` / `e/bw.smali` / `e/au.smali`，全部取自 `b/g` 的四组数组：

| getter | 字段块 | 语义（APK 实证） |
|---|---|---|
| `a(B)` | 8×SHORT `g.d[0..7]` | 基础四维：物攻/物防/法攻/法防（`a/n.ax[4]`，tooltip 按 `ax[i]: 值` 逐行显示，仅显示 >0 的项） |
| `b(B)` | 5×BYTE `g.b[0..4]` | 五行基础值：力量/耐力/敏捷/智力/精神（`a/n.aw[5]`） |
| `c(B)` | 5×BYTE `g.c[0..4]` | 五行加成值；`d(B)=b+c`，tooltip 显示 `aw[i]基础+加成` |
| `e(B)` | 5×INT `g.x[0..4]` | **镶嵌槽（孔）**：`e/ag`/`e/bw` 按控件 `0x4f1a1+i` 绘制 5 个槽；值→`g.b(I)` 把灵石实例 id 段（0x13315480..0x13316bfb 等）映射为孔等级 1..7 |

结论：

1. 1008 单件装备的属性块 = **四维 8 短 + 五行基础 5 字节 + 五行加成 5 字节 + 孔 5 整数**，
   共 23 个属性相关字段；不存在独立的"耐久/强化等级/套装"字段。
   注意 `a/n.ax` 只有 4 个标签：SHORT 槽 4..7 语义未知，真实 APK 数据恒为 0
   （若非 0 会触发 tooltip `aget-object` 数组越界），服务端必须保持 0。
2. 品质不占属性块：客户端用 `b/g.a()` 按模板号查 `a/n.ar[5]`
   （普通/灵器/仙器/古仙器/神器，**无"传说"**）并以 `a/n.at`
   （`*0/*3/*4/*7/*5`）着色；装备与宠物品質数组（`ar`/`as`）分开。
3. 孔固定 5 个槽位（`g.x` 数组长度 5），即单件装备最多 5 孔；
   `g.b(I)` 将灵石 id 段折算为 1..7 阶，非灵石 id 段的值按图标绘制。
4. 强化等级不在此块中：APK 用名称后缀（`+N`）与描述文本表达。

## 原生空孔编码复核（2026-09-19，A/B 级 DEX 实证）

针对本地 APK `piaomiao_local_person_panel.apk` 的 `pmsj/work/e/ag` 直接复核：

- `ag.k()` 固定遍历 5 个控件 `324001..324005`，逐项读取 `g.e(i)`（即
  `g.x[i]` / 1008 字段 34..38）。值为 `0` 时不绘制孔。
- 当值非 0 时，`ag.k()` 调用 `g.b(value)`。若返回 0，则直接使用原始
  `value-1` 作为原生孔位图集 `5813232` 的帧号；若返回非 0，则按灵石等级
  绘制孔位和宝石覆盖层。
- `ag.j()` 寻找可用于镶嵌的空孔时，条件明确为 `1 <= g.e(i) <= 10`。
  因此 **1..10 是“已开但未镶嵌”的原生空孔编码，0 是未开孔**。
- 装备开孔页 `ag.y(1)` 发送 `1009/action=95`；确认开孔 `ag.c_(1)`
  发送 `1009/action=90, equipment_id, material_id`。这证明开孔页与 1008
  孔位数组是同一套原生闭环，而不是 tooltip 文本协议。

本地兼容服当前只需要复现既有 `socket_count` 的原生显示时，按顺序把前 N 个
未占用槽位编码为 `1`，已镶嵌的真实灵石 ID 保持不变。例如 3 个空孔：

`[1, 1, 1, 0, 0]`

该编码用于 `e/ag` 的原生孔位控件。普通装备 tooltip 构建器 `e/b` 不读取
`g.e(i)`，因此 tooltip 本身不会因为 1008 孔位值而额外绘制孔图标；现有
“开孔 N/5”文字仍作为详情兼容显示保留。

## 装备开孔原生闭环（2026-09-19）

APK `pmsj/work/e/ag` 与 `pmsj/work/b/g` 已直接复核：

- 打开装备开孔页：C→S `1009 [short(95)]`。
- 确认开孔：C→S `1009 [short(90), int(equipment_id), int(material_id)]`。
- `g.b(j)` 明确只接受模板 `322250000..322250003` 作为开孔材料；
  这是混沌石材料的客户端硬范围。
- 每次确认只带一个材料实例 ID，因此一次开孔固定消耗 1 颗材料。
- APK 帮助文本锁定：最多 5 孔、第一孔成功率 100%、后四孔普通混沌石成功率
  逐次降低、失败装备无损但材料照常消耗、特殊混沌石例外。
- 原生装备范围仍以 1..10 为准；戒指 11 及本地扩展 12..14 不参与此闭环。

本地兼容服映射：

- `322250000`：混沌石。
- `322250001`：天元混沌石（名称来自历史活动资料，ID 对应为本地映射）。
- `322250002`：三才混沌石（名称来自历史活动资料，ID 对应为本地映射）。
- `322250003`：特殊混沌石兼容项。

普通混沌石本地成功率（万分比）为
`10000, 7500, 5000, 3000, 1500`；第一孔 100% 与 APK 帮助一致，
后四孔精确官方数值尚未找到，因此明确标记为本地兼容规则。
特殊混沌石本地暂按五孔 100% 处理，符合“特殊混沌石除外”的帮助边界，
但不声称是官方概率表。

`1008(operation=3)` 刷新装备；失败不改装备孔位，但仍扣除 1 颗混沌石。
原生空孔编码范围为 `1..10`，但“装备部位→具体孔型”的官方映射尚未锁定。
2026-09-19 真机验证：武器使用值 `10` 时，关闭并重新打开开孔页后孔位显示为
隐藏/暗态；值 `1` 已在真机确认能稳定绘制为已开启空孔。因此当前兼容服统一
使用 `1` 作为新开空孔的占位编码。等取得官方部位→孔型表后，只替换该映射，
不改变 `extra_attributes/g.x[0..4]` 的协议结构。


### 真机回归：开孔页重开与实时刷新（2026-09-19）

清锋剑第一孔成功后，详情页已正确显示 `开孔 1/5`。随后发现此前“武器槽 10
→ 空孔编码 10”的兼容推断会导致：关闭开孔页再进入并放入该武器时，已开孔槽
显示为暗/隐藏；继续成功开第二孔也无法直观看到新增孔位。该现象说明问题在空孔
图形编码而非 `1008` 孔位计数。

已撤销“槽位号=孔型号”的推断，新开的空孔统一写入真机已验证的值 `1`。
仍使用 `1008(operation=3)` 实时回写装备；不新增自定义刷新消息。


### 真机回归：旧孔码迁移与页面实时刷新（2026-09-19）

继续真机验证发现两个独立问题：

1. 清锋剑是在早期“武器槽 10 = 空孔码 10”的错误版本中开出的孔，因此角色存档
   仍可能保存 `[10,...]`。仅修改新开孔代码不会自动修复既有角色。角色加载迁移
   现会把所有 `1..10` 的“空孔编码”统一归一为已验证值 `1`；真实灵石 ID
   （远大于 10）不受影响。
2. 成功开孔后，`1008(operation=3)` 已更新客户端物品对象，但已打开的
   `e/ag` 页面持有已选择控件的缓存，没有立即重绘。成功事务现在在 1008 和
   材料更新之后追加原生 `1009/action=95` 页面初始化响应，要求客户端重新绑定/
   重绘当前开孔页。失败时孔位未变化，不追加该刷新。

测试要求：拉取后必须重新登录一次，让旧 `10` 孔码迁移为 `1`；随后重新进入
装备开孔页验证已开孔可见，并验证新孔成功后页面能立即重绘。
