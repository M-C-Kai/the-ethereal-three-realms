## 查看：1303（`0x517 → :sswitch_eb5` → `e/ey`）

C→S 两种形态均支持：`[byte 2, int actor_id]`（地图菜单）与
`[byte 2, int 0, string 名字]`（好友页/聊天页菜单）。

S→C 使用 **action=1**（e/ey pswitch_11）：查看目标一定在查看者视野内
（`m.n(actor_id)` 可命中），客户端直接复用该 b/v 已有的 1014 属性表
渲染面板（名字/等级/门派/外观/头像全部来自活对象），服务端只补齐
面板专属属性与装备列表。字段布局：

| 字段 | 类型 | 属性 | 语义 |
|---:|---|---:|---|
| 0 | byte | - | action=1 |
| 1 | int | - | 对方 actor id（m.n 查找键） |
| 2 | string | prop54 | 配偶 |
| 3 | string | prop75 | 人气 |
| 4 | int | - | 已装备数量 N |
| 5.. | 6 字段/件 | - | 每件装备 `[int 模板, byte 槽位, string 名字, int 图标, int 实例 id, short 数量]` |
| 末-1 | string | prop79 | 师傅 |
| 末 | int | prop84 | 斗法排名（0=未上榜） |

装备的槽位字节决定面板格子位置（`ag()` 用 `0x17700+k` 定位）；右侧
属性列来自 S→C `1089/2 [byte 2, int 0, byte 0]`（e/ey.b 只读字段 2 的
行数，0 行即刷新；行内容为 `[int 图标, int 数值]` 对，本地服暂不下发）。
注意 1089/action=0 的角色页扩展信息仍由 role 系统应答，social 只剥离
byte-2 形态。首次实现的 action=2（pswitch_5b 从零重建 b/v）已弃用：
面板打开但依赖的 1089/2 附加行未同步导致内容空白。

**APK 协议核查结论**：详见 `docs/development/APK_VERIFICATION_1089_ACTION2.md`（v1.1）
- 证据等级：B级（帧格式闭环）；图标→属性映射仍 C 级待真机标定
- 协议格式：`[byte 2, int 0, byte N, int 图标, int 数值 × N]`（列数=字段2，每列恰2值）
- 解析逻辑：`rows=(size-3)/columns`（每列 [图标,数值] 时 rows=2），列优先交错存放
- 渲染：`ey.k()` 每列 = 数制图标下标 `v0[0].b()` + 数值 `v0[1].b()`（>0 绿 0x38a806 / ≤0 黄 0x38cf16）
- 字段类型：field0=byte action、field1=int 占位、field2=byte 列数、field3+=int 值（`La/c/m`）

## 私聊：1004（`0x3ec → :sswitch_474`）

C→S 布局：`[int 0, short 频道, short 0, int 0, string 对象, string 说话人, string 正文]`。
S→C 由 `main/d.a(S,String,String,String)` 渲染：`e(4)`=说话人（`*4 名字：*3 正文`）、
`e(6)`=正文、`e(5)`=对象。本地服转发规则：

- 频道 `0x7de (2014)` 私聊：按对象名字解析在线角色，定向推送；
  不在线则回 1049"对方不在线，私聊未送达"。
- 其余频道：向同图全部在线玩家广播（字段与 C→S 一致，4/5 交换为说话人/对象）。

## 交易：1056（`0x420 → :sswitch_ad8`）

两阶段确认（其余 7/9/11..19/21/22 的 S→C 更新分支见 e.sswitch_ad8
pswitch_data_1334 与 e/eu.a pswitch_data_146）：

1. **请求**：C→S `1056/1 [byte 1, int 对方 actor id]`；
   S→C `1056/1 [byte 1, int 发起人 actor id, int 0, string 发起人名字]` →
   对方弹"请求交易,是否接受?"（接受→C→S `1056/2`，拒绝→`1056/3`）。
   注意名字必须在字段 3（`w.e(3)` 越界会抛异常），字段 2 必须存在。
2. **开窗**：接受后双向 S→C `1056/5 [byte 5, int 对方 actor id, int 0, int 0]`；
   `e/eu.a` 动作 5 用 c(1) 作为窗口标题"交易 <对方名字>"。
3. **锁定**：C→S `1056/20 [byte 20, int 银两, int 物品数, int*实例id,
   int 对方物品数, int*对方实例id...]`（最后一段是发起方本地看到的对方
   列表，服务端忽略）。服务端向对方推送：S→C `1056/8 [byte 8, byte 数量,
   (int 实例 id, byte 槽位, int 模板, int 数量, int 保留, int 图标)*]`
   （锁定物品行，e/eu pswitch_a7 用行内第 6 个 int 作图标贴图）、
   S→C `1056/6 [int 银两]`、以及 **S→C `1056/10`** —— e/eu pswitch_138
   启用对方在 `c()` 初始化时禁用（`0x3e92` b(false)）的最终确认按钮。
4. **确认与结算**：双方点击确认按钮后各发 C→S `1056/10 [byte 10,
   int 对方 actor id]`；双方都确认后服务端原子结算（余额、物品在背包、
   背包容量、重复提交全部校验后，物品实例整体转移、银两按 `silver`
   货币过账），双方收 1009/3 移除帧、1008/3 入包帧、1017 银两刷新、
   S→C `1056/20`（e/eu pswitch_134 置 ag 完成标记）、S→C `1056/11,12`
   关窗与"交易完成"提示。
5. **失败/取消**：结算校验失败 → 双方"交易失败：原因" + 关窗并清理会话；
   C→S `1056/3` 拒绝与 `1056/4`（窗口关闭 g() 回调）→ 对方 1049 提示。

> 关键教训：C→S 1056/10 **不是取消**。e/eu.c() 把 `0x3e92` 按钮初始化为
> 禁用，锁定后才 `b(true)` 启用；点击它发送 `1056/10`，是两阶段确认的
> 第二阶段。把它当作取消会直接导致"一方确认交易就结束"。

## 赠送：1009/81（`k.a(Lpmsj/work/b/j;)Z`）

服务端校验物品在赠与方背包、对方在线且背包有位，然后整实例转移

## 组队：1023（`0x3ff → main/e.ag`，e/eq 邀请页；systems/team）

- 邀请：C→S `1023/2 [short 2, int 对方 actor id]`；发起方无队时服务端先
  自动建队（等价于 1023/0 创建闭环：1017 {0:0x40} 队长旗 + 1026 自记录）。
  对方收 S→C `1023/2 [short 2, int 队长 role_id, string 队长名, short 等级,
  byte 门派]` → e/eq 邀请页（接受→`1023/3`，拒绝→`1023/4`，均回带队长 role_id）。
- 接受：队伍注册表加入成员。**双方都收 1026/action=0 成员记录**。
  e.aj pswitch_e 把 fields[2:] 整段作为一行加入 `aa.a`，行结构
  （由 e/et 成员页的取值列与 e.aj 的 1017 属性 40-43 回写列反推锁定）：

    row[0] string 名字（成员页第 2 列；旧实现此处误发 byte 计数，
           导致 id 查找/暂离标志全部错位、成员页呈"无队伍"）
    row[1] int    条目 id（aa.a([row])I / et 菜单 / m.o 查找键）——
                  **按接收方定制**：本机自己的行 = raw role id，
                  他人行 = actor id（1_000_000+role_id），与 1038 链同规则
    row[2] int    当前 MP（1017 prop 41 回写）
    row[3] int    当前 HP（1017 prop 40 回写）
    row[4] int    门派 id（成员页第 3 列 → b/v.v(I) 门派名）
    row[5] int    等级（成员页第 4 列）
    row[6] int    MP 上限（1017 prop 42 回写）
    row[7] int    HP 上限（1017 prop 43 回写）
    row[8] int    标志（bit0=暂离；et 状态列）

  第 0 行在成员页 et（0x131）中标"队长"，因此所有客户端 `aa.a`
  都必须队长在首行。队长侧不发 1023/6——那是入队**申请**列表行
  （发错会把 max_hp 当 aM 场景名下标用，越界崩溃）。

- **prop0 队伍状态位（易漏！）**：主菜单"队伍"项按 `b/v.Z()`
  （prop0 & 0x40，队长）|| `b/v.aa()`（prop0 & **0x200000**，队员）
  决定打开成员花名册页（0x5c/er）还是"你目前尚未组队"帮助页
  （0x5b/ep）；成员页自身的队长按钮与点击菜单的暂离/归队/交队项
  也读这两位。因此入队时服务端必须给**队员本人**发
  1017 {0: 0x200000}（队长建队时已收 1017 {0: 0x40}）；离队/被踢/
  解散时清为 {0: 0}；升队长时新队长 {0: 0x40}、旧队长降为
  {0: 0x200000}（不是清零——仍是队员）。缺这一位的表现即
  "已加入队伍但队伍页显示你目前尚未组队"。
- 申请入队：C→S `1023/6 [short 6, int 队长 role id]` → 队长收
  S→C `1023/6 [short 6, int 申请人 id, string 名字, int 等级,
  int 场景 id(<14，aM 下标), int 0]` → 0x51 申请列表页（允许加入→
  C→S `1023/7 [int 申请人 id]`，拒绝加入→C→S `1023/8`）。
- **总则：所有携带成员 id 的 S→C 帧（1026 行、1023/1、17、18、20 与
  1017 旗）都必须按接收方定制 id（自己 raw / 他人 actor）**，
  否则 `aa.b(id)`/`m.o(id)` 在该客户端落空、帧被静默丢弃。
- 暂离/归队：C→S `1023/18|17 [short 18|17]`（无载荷，`w.a(IS)`）；
  服务端向全队广播 S→C `1023/18|17 [int 发起人的条目 id]`
  （e.ag sswitch_c6/105 切换成员 row[8] 的 bit0；17 且 id=自己时客户端
  只清本地行动队列，**不重建跟随链**）。
- 踢出：成员页 et（0x131）菜单"踢出队伍"→确认框(id=1)→
  C→S `1023/12 [int 目标 role id]`。服务端移除后向**所有人**发
  S→C `1023/1 [int 被移除者 id]`——该动作一帧两用：被移除者读到
  id=自己走 `aa.i()` 清空自身队伍状态，其余客户端 `aa.a(id)Z` 移除
  该行并停掉其跟随，随后各自重建 1038 链。（`1023/22`+`aa.g` 是
  申请列表行清理，与成员移除无关。）
- 升为队长：et 菜单"升为队长"→确认框(id=2)→
  C→S `1023/20 [int 目标 role id]`（et 行内为 raw；地图菜单"交队"
  确认(44)发的是**目标 actor id**，服务端两种都收并归一化）。
  服务端把花名册重排为新队长在首（`aa.a` 第 0 行在成员页标"队长"），
  向每个客户端发 S→C `1023/20 [新队长的条目 id]`（按接收方定制，
  `aa.d(id)` 才能在本机行内命中），再向每个客户端发
  1017 {0:0x40}（指向新队长的条目 id）与 1017 {0:0x200000}（指向
  旧队长的条目 id，降为队员位而非清零）——新队长的 `Z()` 与旧队长
  的 `aa()` 由此立起，成员页的队长专属按钮随 prop0 同步显隐——
  最后全队重发 1038 链（链头=新队长）。
- 召集队员：et 菜单"召集队员"仅对**暂离**成员可发
  （未暂离客户端直接提示"当前队员并未暂离队伍！"）→
  C→S `1023/19 [int 目标 role id]`。服务端清除其暂离标志，向全队
  广播 S→C `1023/17 [int 目标 id]` 并重发 1038 链——召集的本质是
  把离队跟随链的成员拉回链上，而非传送。
- 上限 3 人；对方已有队伍、重复邀请、60 秒过期均以 1049 提示拒绝。
- **按钮显隐排查结论**：加入队伍后客户端没有任何界面会隐藏操作
  按钮；全部按钮显隐都是 prop0 0x40（队长旗）或窗口自身状态驱动：
  ①成员页 et 的"允许申请/解散"按钮仅在 `ab.Z()`（prop0 0x40）时
  显示；②成员行菜单队长 8 项/队员 5 项；③地图点击菜单按队伍状态把
  "组队"换成"暂离/归队/交队"；④交易窗口锁定后禁用自身按钮。
  早期"按钮消失/无响应"的观感来自旧实现入队通知缺 1026（队长端
  花名册不更新）与 1023/6 行 aM 下标越界中断处理器，均已修复。

### 跟随链：1038（`0x40e → main/e.ai`）

成员跟随的实现帧是 **S→C 1038**，不是 1028（0x404 在 APK 主接收
分发表中不存在，发了会被静默丢弃）。`e.ai` 布局：

| 字段 | 类型 | 语义 |
|---:|---|---|
| 0 | int | 链头（队长）id |
| 1/2 | int | 保留 0 |
| 3/4 | int | 链头落点 x/y |
| 5 | byte | 链员数 N |
| 6.. | int×N | 链员 id（按跟随顺序） |

`e.ai` 行为：`m.m()` 守卫（地图已加载）→ `m.o(链头)` 置 H=true →
逐个链员 `E()` 停走、置 H=false、按序 `a(n)` 挂链（头.J=员1，
员1.J=员2……尾.J=null）→ 头非本地或未在走路时 `b(x,y,false)` 走位；
头是本地玩家且正在移动时只挂链不覆盖输入走位。`b/m.o(I)` 的查找
规则决定 **id 必须按接收方定制**：本地玩家匹配 raw role id，其他
玩家匹配 actor id（1_000_000+role_id）。因此队长客户端收到
[队长 raw id; 队员 actor id]，队员客户端收到 [队长 actor id;
自己 raw id 放链表首位; 其余队员 actor id]。

服务端下发时机：入队/归队(17)确认后向全队每个在线客户端发送一次；
之后**队长每次移动**（地图可见性推送处）用 1038 替换普通 1005 发给
跟随者——普通 1005 分支会调用 `v.ad()` 把 J 重置为宠物链接（拆链），
所以链必须随移动持续重发。队员的真实坐标仍以其随后上报的 1005 为准。
## 切磋 1157 与 PK 1158（双人即时对决，接入战斗系统）

- 切磋：C→S `1157/2 [byte 2, int 自己 role id, int 对方 actor id]` →
  对方收 S→C `1157/1 [byte 1, int 发起人 actor id, int 对方 actor id, int 0]`；
  `e/cu.a` 未处于观战模式时读取字段 1..3 的三元组并自动回发
  C→S `1157/4 [byte 4, int 发起人 actor id, int 自己 actor id]`——这是
  目标客户端的隐式应答通道。
- PK：C→S `1158/2 [byte 2, int 自己 role id, int 对方 actor id]` →
  对方收 S→C `1158 [byte 0, int 0, int 发起人 actor id]` →
  e.sswitch_e56 弹"确认要PK吗?"（确定→C→S `1158/6 [byte 6, int 自己 role id,
  int 发起人 actor id]`；拒绝仅关窗，无 C→S）。
- **对决**：双方确认后由战斗系统创建共享 `PvpDuel`（真实装备攻防/血量），
  双方客户端各自收到与 PVE 相同的进入序列
  （`1040/0` 复位建屏 → `1048` 参与者（本方 kind=1/side=2，
  对手 kind=2/side=1、source_model=模型-1，故对手仍以玩家造型出现）→
  `1040/1` 首回合），随后走原生战斗协议：
  任一方的 `1041` 指令（1=攻击、2=防御）推进一个共享回合，服务端结算
  攻击 + 对方反击（防御时反击减半），把同一批 `1042` 动作帧广播给双方
  并各补一个 `1040/2` 播放推进帧；每回合后重发双方 `1048` 同步血条。
  一方血量归零即结束：双方收 `1040/4` 与胜负 1049；`1041/6` 逃跑视为
  弃战（发起方走原生 `1041/10` 逃跑动画，对方收结束帧与提示）。
  断线时由 `abandon_duels` 清理并通知对手。切磋与 PK 目前共用同一套
  结算规则，无经验/掉落与红名惩罚。

## 与其他系统的边界

| 消息 | 归属 | 说明 |
|---|---|---|
| 1023/0、1023/11 | role 系统 | 连接内单人建队/解散闭环（连接本地 `LocalTeamState`） |
| 1089/action≠2 | role 系统 | 角色页扩展信息（`character_extension_info`） |
| 1009/action≠81 | inventory 系统 | 丢弃/使用/装备/强化等物品动作 |
| 1303、1019、1056、1157、1158、1004 | social 系统 | 本文档全部链路 |

装配顺序（`server.py`）：social 必须先于 role 与 inventory 注册，
`tests/test_system_architecture.py` 的 RouterPriorityTests 固化了该约束。
