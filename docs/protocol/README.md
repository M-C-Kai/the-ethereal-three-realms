# 当前游戏通信协议全景

> 审计对象：`implementation_staging` 中的 Python 本地兼容服务器、测试客户端及随仓库保存的 APK smali 证据。结论以当前代码为准；`已确认` 表示有可定位代码，`待确认` 表示现有静态证据不足。本目录不描述官方服务器协议，也未修改任何运行代码。

| 问题 | 当前答案 |
|---|---|
| 网络协议 | TCP 长连接；登录服和游戏服共用配置端口 `6805`，客户端会断开登录连接后再次连接游戏阶段（已确认） |
| 序列化 | 自定义大端二进制 TLV 字段流（已确认） |
| Packet | `uint16 frameLength` + `uint16 messageId` + 0..N 个带 1 字节类型标记的字段；长度包含自身（已确认） |
| CMD 定义 | 无集中枚举；ID 分散于 `server.py` 编码器/分发分支、`test_client.py` 发送点和 APK smali（已确认） |
| 当前代码涉及消息 ID | 覆盖范围持续扩展，具体以消息号总表及实现审计为准；已包含队伍最小闭环 `1023/1026`（已确认） |
| APK 完整静态协议面 | 120 个唯一 ID：110 个有 APK 接收分支，91 个有 APK 发送构造（已确认） |
| Push | 至少 12 个 S→C-only ID；另有多个双向 ID 的服务端主动 action（已确认） |
| 同步模型 | 服务端权威的事件/状态增量同步；地图以分段状态下发，战斗以动作批次+播放屏障推进；不是 frame/tick 锁步（已确认） |
| 心跳 | 游戏握手后服务端每 25 秒发 `1012(int nonce)`；客户端同 ID 回应（已确认） |
| 断线重连 | 没有恢复协议；内存 session 可再次握手但连接内战斗状态丢失，未见 lastSeq/snapshot 补发（已确认/能力边界） |

协议模块：登录与选服、角色与人物、地图与对象、物品、战斗、资源、菜单占位、心跳，以及队伍创建/解散的单人最小闭环。当前代码没有大厅、匹配、多人组队或房间协议。

## 计数口径

“消息 ID”按线上的 `uint16 messageId` 去重，不把 action/subtype 拆成新 ID。方向按当前 Python 服务端是否实际接收/发送计算；测试和诊断构造器但未进入服务端运行发送链的内容不计为活跃协议。来源：`implementation_staging/server.py:571-1696,1865-2449`、`implementation_staging/test_client.py:11-350`。
