## 1. 孔属性映射表

根据当前项目用户提供的原版资料，曜灵石体系应按 **金、木、水、火、土、炎、玄、魔** 八种属性理解，
另有一颗非曜灵石系、但同样参与镶嵌的 **佛骨舍利**。

客户端 `g.x[0..4]` / 1008 fields[34..38] 仍是五个孔位的当前显示状态：

- `0`：未开孔。
- 空孔状态：客户端使用 `1..10` 范围中的孔型编码绘制颜色/类型。
- 已镶嵌状态：孔位值替换为对应宝石模板值。
- 真机已经确认值 `1` 可作为“已开空孔”稳定显示，但这只是兼容占位，不代表真实孔色。

### 原版孔色与宝石效果

| 宝石 | 对应孔色 | 效果 |
|---|---|---|
| 金曜灵石 | 金色孔 | 提高物理攻击 |
| 木曜灵石 | 青色孔 | 提高物理防御 |
| 水曜灵石 | 蓝色孔 | 提高出手速度 |
| 火曜灵石 | 红色孔 | 提高法术攻击 |
| 土曜灵石 | 青色孔 | 提高法术防御 |
| 炎曜灵石 | 黄色孔 | 提高爆击 |
| 玄曜灵石 | 黑色孔 | 提升技能 |
| 魔曜灵石 | 紫色孔 | 增加储物空间 |
| 佛骨舍利 | 青色孔（同青色系兼容） | 生命类效果；非曜灵石系 |

因此颜色维度实际是 7 色：

- 金：金曜
- 青：木曜、土曜、佛骨舍利
- 蓝：水曜
- 红：火曜
- 黄：炎曜
- 黑：玄曜
- 紫：魔曜

这与 APK `g.b(value)` 对已镶嵌宝石的 1/3/4/5/6/7 等绘制类别存在可对应关系；
但 **空孔码 1..10 到具体颜色的官方映射仍未完全锁定**，不能再用“装备槽位号=孔型号”的方式推断。

### 顺序约束

APK 帮助文本明确：

1. 第 1 颗宝石进入第 1 孔：正北位（天极）。
2. 第 2 颗进入第 2 孔：正西位（觉醒）。
3. 第 3 颗进入第 3 孔：正东位（元乙）。
4. 第 4 颗进入第 4 孔：西南位（八荒）。
5. 第 5 颗进入第 5 孔：东南位（九幽）。

因此服务端不得允许跳孔镶嵌；目标孔应为“按下标扫描得到的第一个已开且未镶嵌孔”。

每族 12 个模板，和 APK 帮助“曜灵石一共有 12 阶”吻合：

`template_id = family_base + (rank - 1)`，其中 `rank = 1..12`。

### 客户端筛选结论

`ag.r() -> ag.b(3)` 在“装备镶嵌”模式下调用 `g.e(item)`，因此上述 9 族会进入客户端宝石候选列表。

**客户端并没有在确认镶嵌前本地完成“孔色 ↔ 宝石族”的最终裁决。**
确认包只携带装备实例 ID 和宝石实例 ID，不携带孔号。
这意味着原版的孔色匹配和“第一个可镶孔”选择属于服务端规则。


### 名称纠正

此前分析文档把部分 3220001xx/3220002xx 族误记为“月曜/月冥”，并把
322003xxx/322005xxx/322006xxx 错记为“金曜/木曜/土曜”。现按原版资料统一纠正为：

`木曜 / 土曜 / 金曜 / 火曜 / 炎曜 / 水曜 / 玄曜 / 魔曜` 八曜，
加 `佛骨舍利` 一类非曜灵石镶嵌物。

## 下一阶段服务端事务边界

### 镶嵌
1. 校验装备属于可镶嵌原生装备。
2. 从 `g.x[0..4]` 顺序查找第一个“已开空孔”。
3. 根据空孔孔型判断宝石族是否兼容。
4. 校验宝石模板属于上述九族之一。
5. 消耗 1 颗宝石。
6. 将目标 `g.x[index]` 从空孔码替换为宝石模板值。
7. 保存。
8. 发送装备 1008(operation=3)、宝石数量更新/删除、原生页面刷新。

### 拆除
1. 请求直接给出 `socketIndex`。
2. 校验该孔确实已镶嵌宝石。
3. 收取 1000 银两（APK 帮助文本明确）。
4. 把对应宝石作为物品返还背包。
5. 恢复原孔型，而不是写死为 1。
6. 保存并发送 1008/背包更新/页面刷新。

因此在进入镶嵌实现前，装备实例必须能持久化每个孔的原始孔型；仅靠当前
`extra_attributes/g.x[]` 在“已镶嵌”状态下无法反推出拆除后应恢复的孔色。
