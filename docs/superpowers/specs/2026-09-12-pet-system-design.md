# 宠物系统完整设计

## 目标

在当前本地兼容服已经打通的宠物列表、详情、出战/待命、溜宠/隐藏和地图跟随基础上，完成 APK 原生宠物系统的服务端闭环。所有功能必须优先使用 APK 已存在的原生界面、原生消息号、原生字段顺序和字段类型；协议证据未闭环的功能不得通过猜测字段、伪造消息号或客户端补丁绕过。

最终目标是让手机端能够使用原生宠物 UI 完成宠物管理、技能、战斗召宠/召回、捕捉、仓库、培养和交易/寄售，并且所有状态都由本地服务器权威持久化。

## 已确认基础

当前主分支已经具备以下宠物链路：

- `1127/action=1`：创建宠物实例并加入客户端 `pmsj/work/b/f.k`。
- `1127/action=9`：下发宠物属性详情，覆盖 property 30～90。
- `1103/action=10`：宠物第二层详情/技能容器请求入口，当前返回空技能容器。
- `1130/action=10`：出战/待命请求，持久化并通过 `1134` 同步 property 11。
- `1130/action=48`：溜宠/隐藏请求，持久化并通过 `1134` 同步 property 12。
- `1127/action=13`：把已有 `b/u` 宠物挂到地图人物 `b/v.E`，客户端执行 `pet.b()` 和 `player.ae()` 后显示跟随宠物。
- `1010/action=102`：清理地图人物 `b/v.E`，隐藏跟随宠物。
- `property 2` 已确认是宠物主体 `assets/res/role/<id>.dat` 资源 ID；当前测试宠物使用已验证可渲染的 `5860000.dat`。

客户端核心对象已经确认：

- `pmsj/work/b/u`：宠物实体，继承 `b/n`。
- `pmsj/work/b/f.k`：玩家宠物集合。
- `pmsj/work/b/v.E`：地图人物挂载的跟随宠物。
- `pmsj/work/b/h`：战斗参与者对象，宠物战斗时进入该链。
- `pmsj/work/e/co`：宠物主菜单。
- `pmsj/work/e/cn`：宠物列表与出战/溜宠控制。
- `pmsj/work/e/ci`：宠物属性/加点。
- `pmsj/work/e/cj`：宠物基础/成长资料。
- `pmsj/work/e/ck`：宠物合成/炼化。
- `pmsj/work/e/cf`：宠物进化。
- `pmsj/work/e/j`：战斗召宠、召回、捕捉。

## 核心原则

1. **APK 原生协议优先**：每个新 handler 在实现前必须从 DEX/smali/JAR 确认消息号、子命令、字段顺序、字段类型和客户端状态变化。
2. **服务端权威**：宠物等级、经验、HP/MP、技能、资质、成长、寿命、出战、溜宠、仓库位置、培养结果、交易状态均以服务器数据为准。
3. **真实宠物实例**：捕捉、仓库存取、合成、交易都操作同一个 `pet_id` 实例；禁止按模板复制一个“看起来一样”的宠物代替实例转移。
4. **模板与实例分离**：`data/pets.json` 保存种族模板；角色存档中的 `pets[]` 保存玩家拥有的实际宠物。
5. **向后迁移**：现有 `data/roles.json` 不删除、不覆盖；新增字段必须幂等迁移。
6. **一次只开放一个可真机验收闭环**：每个功能域都必须先有协议测试，再由用户手机验证原生 UI。
7. **不扩大 `server_pets.py`**：该文件最终只做路由安装和与现有 server 的桥接，不承载复杂业务规则。
8. **标准库优先**：服务端继续只依赖 Python 标准库。

## 模块边界

最终结构：

```text
pet_registry.py                 # 宠物模板读取/校验
pet_model.py                    # 宠物实例 schema、迁移、查找、ID 分配
pet_service.py                  # 核心宠物业务：改名、放生、状态、加点、经验
pet_protocol_core.py            # 1127/1130/1134 等核心协议
pet_walking_protocol.py         # 地图跟随 attach/detach

pet_skill_registry.py           # 技能模板
pet_skill_service.py            # 学习、替换、技能持久化
pet_protocol_skill.py           # 技能 UI 协议

pet_battle.py                   # 召宠、召回、宠物战斗参与者、结算
pet_protocol_battle.py          # 战斗相关宠物帧

pet_capture.py                  # 捕捉判定、生成实例、容量检查
pet_storage.py                  # 宠物仓库存取和容量
pet_protocol_capture.py
pet_protocol_storage.py

pet_training.py                 # 合成、炼化、进化、顿悟/成长
pet_protocol_training.py

pet_market.py                   # 宠物寄售/购买/上交
pet_protocol_market.py

server_pets.py                  # 只安装路由和桥接现有 server
```

如果后续 DEX 证明某些功能使用同一消息和同一状态机，可以合并协议文件；不为了“文件数量少”把不同业务重新塞回一个大文件。

## 功能域 1：宠物核心

必须完成：

- 列表与详情
- 改名
- 放生
- 出战/待命
- 溜宠/隐藏
- 属性加点
- 等级/经验升级
- HP/MP、寿命
- 顿悟点、悟修、神通/品阶显示
- 背包容量与唯一出战/唯一溜宠约束

规则：

- 同一角色最多一个 `deployed=true`。
- 同一角色最多一个 `walking=true`。
- 被放生、寄售、仓库存放的宠物不能保持出战或溜宠状态。
- 改名、加点、升级必须立即持久化，并通过 APK 已确认的增量帧刷新 UI。
- 放生必须先取消出战/溜宠，再从有效宠物集合移除。

## 功能域 2：宠物技能与战斗

必须完成：

- 技能列表和详情
- 技能学习/替换
- 战斗召宠
- 战斗召回
- 宠物以 `1048` fighter 进入战斗
- 宠物普通攻击和已确认技能
- HP/MP 消耗、死亡、战斗结束恢复规则
- 宠物经验结算

APK 已确认战斗菜单存在召宠/召回/捕捉；`main/b` 在召宠动作中会按 pet id 从 `b/f.k` 找宠物，再关联/创建 `b/h` 战斗对象。实现前必须锁定实际 C→S 命令字和 S→C `1042/1048` 字段。

第一版不发明未确认的伤害公式；可以使用本地服明确记录的兼容公式，但客户端表现字段必须使用原生协议。

## 功能域 3：捕捉与宠物仓库

捕捉：

- 只允许在 APK 原生“捕捉”动作触发后处理。
- 目标必须是当前战斗中允许捕捉的怪物。
- 成功后分配全局唯一 `pet_id`，创建真实宠物实例并下发到 `b/f.k`。
- 失败不能生成实例。
- 宠物背包满时返回 APK 原生失败表现，不丢状态。

仓库：

- `bag -> storage` 保留同一 pet id。
- `storage -> bag` 保留同一 pet id。
- 仓库中的宠物不能出战、溜宠或进入战斗召宠列表。
- 存取过程中失败必须保持原 location。

## 功能域 4：培养

包含：

- 合成
- 炼化
- 进化
- 顿悟/悟修
- 妖兽→灵兽→圣兽→仙兽→神兽成长阶
- 资质和成长变化
- 材料消耗

已经确认合成/炼化 UI 会检查主副宠寿命 property 59 大于 10。其余消耗、概率、结果字段必须从客户端协议或明确本地规则取得证据后再实现。

培养操作需要事务化：宠物实例和物品材料要么一起成功，要么都不改变。

## 功能域 5：经济

包含：

- 宠物交易
- 宠物寄售搜索
- 上架
- 下架
- 购买
- 上交

复用现有物品寄售的持久化和事务基础，但宠物 listing 不得伪装成 `ItemInstance`。宠物上架后 `location=consignment`，从宠物背包列表中消失；购买时同一 pet id 转移给买家角色。

已有物品寄售设计中对 `object_type=3` 的“不支持”将在本域完成后替换为真实宠物市场逻辑。

## 协议研究门槛

每一个功能上线前必须形成一条 protocol lock 记录，至少包含：

- 客户端发送方方法/类
- 消息号
- 子命令
- 每个字段的读取/写入方法，对应 byte/short/int/string/binary
- 服务端响应的客户端 dispatcher 分支
- 客户端响应后改变的对象/字段/UI
- 一条编码/解码单元测试

未达到以上条件的功能只能保留为“协议研究”，不能进入运行时 handler。

## 迁移策略

现有角色第一次进入新版本时：

- 保留现有宠物 ID、名称、等级、出战/溜宠状态。
- 缺少 `location` 时补 `bag`。
- 缺少 `skill_ids` 时补空列表。
- 缺少 HP/MP 时按当前模板/等级计算初始值。
- 缺少培养和交易字段时补安全默认值。
- 不重新赠送第二只测试宠物。

迁移必须幂等，第二次运行不再改变数据。

## 测试策略

每个功能都遵循 TDD：

1. 先写失败测试。
2. 确认失败原因是目标行为缺失。
3. 写最小实现。
4. 运行目标测试。
5. 运行全部 `python -m unittest discover -s tests -v`。
6. 网络行为变更再运行 `test_client.py`。
7. 用户真机验证 APK 原生 UI。

核心回归至少长期覆盖：

- 旧角色迁移不重复宠物
- 1127 property 2 使用真实可渲染 dat
- 唯一出战/唯一溜宠
- 地图 attach/detach
- 放生不能留下悬挂状态
- 仓库存取保持 pet id
- 捕捉只生成一个真实实例
- 战斗召宠按 pet id 找到同一实例
- 交易/寄售转移同一 pet id
- 合成/炼化失败不消耗宠物或材料
- 服务重启后所有宠物状态一致

## 实施顺序与验收门

### 阶段 A：核心完整化

真机能够完成：宠物列表 → 属性 → 加点 → 改名 → 出战/待命 → 溜宠/隐藏 → 放生，并在重新登录后状态一致。

### 阶段 B：技能

真机宠物技能页显示真实技能，学习/替换后刷新并持久化。

### 阶段 C：战斗

真机进入战斗后可召宠、宠物出现、行动、召回，战斗结束后 HP/MP/经验持久化。

### 阶段 D：捕捉与仓库

真机可以捕捉一个允许捕捉的怪物生成真实宠物，并在仓库存入/取回后保持同一实例。

### 阶段 E：培养

真机可使用原生合成/炼化/进化页面完成至少一条真实培养闭环，结果持久化。

### 阶段 F：经济

真机可通过原生交易/寄售 UI 转移真实宠物实例，并且重启后市场和所有权一致。

只有前一阶段的单元测试、协议测试和用户真机验收通过，才进入下一阶段；但协议逆向研究可以提前并行进行。

## 完成定义

“完整宠物系统完成”必须同时满足：

- APK 原生宠物菜单中上述功能都有服务端真实响应，不再依赖空容器或假成功。
- 所有宠物状态可持久化并能跨重启恢复。
- 地图和战斗使用同一个宠物实例 ID。
- 捕捉、仓库、培养、交易不会复制或丢失宠物实例。
- 任何已实现的 wire frame 都有字段类型单元测试和 DEX/smali 证据。
- 全量单元测试通过，网络回归通过，用户完成每个阶段的手机验收。
