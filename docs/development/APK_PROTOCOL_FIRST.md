# APK 协议优先开发规范（APK Protocol First）

版本：1.0  
适用范围：整个 `M-C-Kai/the-ethereal-three-realms` 仓库。  
适用对象：所有人工开发者、ChatGPT、Codex、OpenCode、Claude、Gemini、自动化 Agent 及其他智能体。

## 1. 总原则

**APK 是客户端契约基准。**

本项目的服务端、资源映射和本地兼容逻辑必须适配现有客户端；不得为了方便服务端实现而重新定义客户端协议、字段或状态机。

任何修改都必须先做 APK 影响复核。这里的“任何修改”包括但不限于：

- 新增玩法或功能；
- Bug 修复；
- 模块拆分、模块迁移、重构；
- MessageID / Action / Property 路由调整；
- 字段数量、顺序、类型、默认值调整；
- 资源 ID、DAT/PNG、地图/NPC/宠物/装备模型映射调整；
- 存档 schema 和资料库结构调整；
- 测试与协议文档的语义变更。

纯内部改动也必须完成复核并证明 APK 契约与客户端可观察行为不变。

---

## 2. 证据等级

每个协议结论、字段语义、资源映射或客户端行为都必须标注证据等级。

### A 级：已确认

直接证据充分，通常包含至少两类相互独立的证据，例如：

- APK/JAR 发送端或接收端调用链；
- 字段读取/写入类型与顺序已确认；
- 资源加载函数与实际资源文件对应；
- 用户真机验证与静态证据一致。

A 级结论可作为正式兼容契约。

### B 级：高可信

关键行为已由 APK 静态证据直接确认，足以实现目标路径，但仍有非关键字段或边缘语义未知。

要求：

- MessageID/Action 必须确认；
- 本次修改实际使用的字段顺序和类型必须确认；
- 未知字段不得创造语义，必须保持已验证安全默认值并标注 TODO/unknown；
- 实现后仍需真机验收时必须标记 `pending real-device verification`。

B 级达到实现门槛。

### C 级：推测

只确认了部分调用、消息号或界面关联，但关键字段、状态转换或业务语义仍无法闭环。

C 级只允许：

- 继续反编译/逆向；
- 增加不改变协议行为的诊断日志；
- 抓取本地客户端与本地服务之间的测试流量；
- 补证据文档或待确认测试夹具。

**不得实现业务语义。**

### D 级：未知

缺少 APK 直接依据，或仅来自猜测、旧私服经验、字段名联想、通用 MMORPG 设计。

**禁止实现。**

## 3. APK Verification Gate

任何实现开始前必须完成以下检查，并在任务记录/提交说明中保留结果：

1. **影响范围**：是否影响客户端可观察行为？
2. **协议对象**：涉及哪些 MessageID、Action、Property、字段、资源、UI 页面或状态机？
3. **客户端发送链**：若是 C→S，请定位构造/发送方法及字段写入顺序与类型。
4. **客户端接收链**：若是 S→C，请定位 dispatcher、action 分支、字段读取顺序与类型，以及最终写入对象/UI/资源的路径。
5. **资源链**：涉及 DAT/PNG/map/icon/model 时，必须确认 ID 到实际资源的加载规则，不能只凭文件名相似。
6. **证据等级**：A/B/C/D。
7. **实现门槛**：A/B 可实现；C/D 停止业务实现。
8. **回归保护**：需要哪些单测、集成测试或协议字节级断言？
9. **真机状态**：已验证 / 待用户真机验证。

---

## 4. Protocol Review 固定流程

任何新增或修改协议行为必须按以下顺序：

`APK/JAR → MessageID → Action/子类型 → Handler/dispatcher → 字段读取/写入 → 对象/状态 → UI/资源行为 → 协议文档 → 测试 → 服务端实现 → 真机验证`

禁止先写服务端再反向寻找“看起来能解释”的 APK 证据。

### C→S 复核至少记录

- 发送方法/调用类；
- 消息号；
- Action/子类型；
- 每个字段的 index、TLV 类型、语义（未知则写 unknown）；
- 触发该发送的 UI/操作。

### S→C 复核至少记录

- dispatcher 类/方法；
- action 分支；
- 每个字段的 index、TLV 类型；
- 写入的客户端对象字段；
- 最终 UI、actor、资源或状态变化。

---

## 5. 字段与 Property 规则

- `byte`、`short`、`int`、`long`、`string`、`binary` 类型必须严格匹配客户端读取方法。
- 数值相同不代表类型可互换。
- 不得因为服务端值较小而把 `int` 改成 `short/byte`。
- 每个新增 Property 必须记录：Property ID、APK 读取/写入位置、类型、含义、使用页面/对象、证据等级。
- 未知 Property 可以透传/保持默认值，但不能命名成未经证实的业务概念。

---

## 6. Action 与消息号规则

每个 MessageID 的 Action 表应逐步形成锁定清单：

- Action ID；
- C→S / S→C 方向；
- 字段布局；
- APK 调用链；
- 当前证据等级；
- 实现状态；
- 真机验证状态。

禁止新增 APK 中没有证据的 Action，禁止为了“复用消息号”创造本地私有客户端语义。

---

## 7. 资源与资料库规则

物品、技能、宠物、NPC、怪物、地图、Buff、任务等静态定义优先进入资料库/registry。

业务代码不得散布诸如：

```python
if template_id == 123456:
    ...
```

除非该分支本身是协议/兼容分流，并且有 APK 证据和说明。

资源 ID 必须区分逻辑 ID、模板 ID、图标 ID、模型 ID、DAT/PNG 资源 ID、装备槽等不同命名空间；不得因为数字“看起来像”就互相替代。

---

## 8. 重构也必须复核

“只是重构”不是跳过 APK Verification 的理由。

纯内部重构必须证明：

- MessageID/Action 路由未改变；
- 字段数量/顺序/类型未改变；
- 下发帧字节语义未改变；
- 状态迁移结果未改变；
- 资源映射未改变；
- 相关旧测试继续通过，必要时增加 golden frame / decode 断言。

如果重构过程中发现旧实现本身与 APK 不一致，必须将“重构”和“协议修复”分开记录，并给协议修复补证据。

---

## 9. 测试要求

协议相关测试至少覆盖受影响的：

- MessageID；
- Action/子类型；
- 字段数量；
- 字段顺序；
- 字段 TLV 类型；
- 关键 Property 数量与值；
- 状态迁移；
- 持久化迁移；
- 重复请求/非法请求不会误扣物品或破坏状态。

测试只能证明“实现符合已定义契约”，不能单独证明“契约来自 APK”。APK 依据必须独立存在。

`implementation_staging/` 的统一验证仍以其 `AGENTS.md` 指定命令为准。

---

## 10. 真机验证规则

真机验证是 A 级证据的重要组成部分，但不能由智能体虚构。

- 用户负责手机/真机验收时，智能体必须明确写出测试步骤和预期现象。
- 在用户确认前，状态写为 `pending real-device verification`。
- 单元测试、模拟客户端、日志正常、CI 通过均不能替代真机结论。

---


---

## 12. 提交与交付要求

涉及协议或客户端可观察行为的提交说明应至少包含：

- `APK evidence:` 证据来源与等级；
- `Protocol impact:` MessageID/Action/Property/资源影响；
- `Tests:` 实际运行的测试；
- `Real-device:` verified 或 pending。

如果证据为 C/D，提交只能是逆向资料、诊断或文档，不能包含对应业务实现。

---

## 13. 安全边界

本规范只允许使用：

- 用户提供的 APK/JAR/反编译产物；
- 本仓库代码、资源和日志；
- 本地测试客户端与本地兼容服务。

禁止访问、扫描、认证、修改或抓取官方/第三方服务器及其非公开数据。

---

## 14. 规则优先级

本规范是项目级开发门禁。

若子模块文档与本规范冲突：

1. 用户当前明确指令优先；
2. 根 `AGENTS.md` 与本规范优先于普通 README/历史交接文档；
3. 子目录 `AGENTS.md` 可以增加更严格规则，但不能放宽本规范的 APK 证据门槛。

任何智能体在未阅读并遵守本规范前，不应修改本项目。
