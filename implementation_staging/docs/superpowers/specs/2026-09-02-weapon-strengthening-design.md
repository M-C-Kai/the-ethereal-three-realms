# 武器强化本地兼容实现设计

日期：2026-09-02

## 目标与边界

在不修改 APK、不新增 messageId、不改变现有 1008 字段数量和类型布局的前提下，实现原生“装备强化”页面可使用的武器强化闭环。服务端沿用 messageId 1009 的 action 97、75、77、74、92、78，并在强化事务结束时复用既有 1008 operation=3 和物品删除动作刷新客户端。

本轮只开放已由项目和 APK 共同确认的武器槽 10。武器可以位于背包或已装备位置，但不能来自仓库。幸运开孔不实现；保留明确 TODO，等待 socket 字段和概率被协议锁定。

## 已确认协议

- 打开页面 C→S：`1009 [short(97)]`
- 选择装备 C→S：`1009 [short(75), int(equipment_instance_id)]`
- 选择强化石 C→S：先发送 action 77，再发送 action 74；两者均携带装备和强化石实例 ID。
- 执行强化 C→S：`1009 [short(92), int(equipment_instance_id), int(stone_instance_id), byte(stone_count)]`
- S→C action 97：`[short(97), string(text)]`
- S→C action 75：`[short(75), string(text)]`
- S→C action 74：`[short(74), short(per_stone_rate), string(text)]`
- S→C action 77 是客户端清槽指令：`[short(77), byte(0)]` 清强化石槽，
  `[short(77), byte(1), byte(1)]` 会清空武器和强化石全部选择。有效材料的 C→S
  action 77 保持静默，由紧接着的 action 74 概率响应完成等待；非法材料才回 status 0。
- S→C action 78：`[short(78)]`

客户端没有 S→C action 92 处理分支。收到 action 92 后绝不返回 action 92。

## 模块边界

新增 `strengthening.py`，作为纯标准库规则模块，集中包含：

- `StrengtheningStoneDefinition`
- 强化石模板常量和定义映射
- 成功率表
- 武器强化奖励表
- 强化石识别与等级解析
- 强化失败等级计算
- 从基础属性确定性重算有效属性
- 可注入 RNG 的成功判定

`server.py` 保留网络与持久化职责：

- 按当前角色重新查找实例并验证所有权、位置、类型、数量和等级
- 处理 1009 action 路由
- 在所有验证通过后一次性修改武器与强化石
- 先保存角色，再发送客户端刷新帧
- 继续保留现有 action 3、4、5、6、82 行为

服务端不保存“当前选中的装备/强化石”连接状态。action 92 完全以请求中的实例 ID 为准并重新验证，避免过期选择或伪造请求。

## 强化石定义与发放

默认本地兼容映射：

| 等级 | 模板 ID | 名称 | 初始数量 | 最大堆叠 |
|---|---:|---|---:|---:|
| initial | 322260000 | 初级强化宝石 | 1000 | 9999 |
| middle | 322261000 | 中级强化宝石 | 1000 | 9999 |

代码注释必须明确说明：模板 ID 为本地兼容映射，属于 APK 原生接受范围，具体旧官方名称与 ID 对应关系尚未静态确认。

`is_strengthening_stone(item)` 同时要求模板位于 `322260000..322261002` 且存在于本地定义映射。仅位于范围内但没有定义的模板不会被服务器接受。

强化石使用固定、按角色派生的实例 ID，位置为 `bag`，普通物品分组为 150。角色增加 `strengthening_stones_initialized` 标记：

- 新角色创建时直接拥有两种强化石并将标记置为 true。
- 旧角色首次迁移时只补充缺失的两种强化石，每种 1000 颗，然后置标记。
- 标记为 true 后，已经消耗完并删除的强化石不会在后续登录时重新生成。
- 已存在的强化石数量不被登录迁移重置。

## 本地兼容成功率

所有概率使用 0..10000 basis points。下表不是旧官方概率表：

| 当前等级 | +0 | +1 | +2 | +3 | +4 | +5 | +6 | +7 | +8 |
|---|---:|---:|---:|---:|---:|---:|---:|---:|---:|
| 初级 | 2000 | 1800 | 1600 | 1400 | 1200 | 1000 | 800 | 600 | 400 |
| 中级 | 2500 | 2200 | 2000 | 1800 | 1600 | 1400 | 1200 | 900 | 600 |

中级在每一级均不低于初级。所有单颗概率均不超过 2500，以满足 APK 的
`min(5, floor(10000/rate)+1)` 计算并开放 1～5 颗选择。多颗强化石成功率按 APK
数量 UI 的强静态推断实现：

`total_rate = min(10000, per_stone_rate * stone_count)`

这不是旧官方概率公式。服务端强制 `1 <= stone_count <= 5`。随机判定封装在 `strengthening_success(..., rng=...)` 中，生产环境使用标准库 RNG，测试注入确定性 RNG。

## 强化等级与失败规则

每件装备持久化：

- `strengthen_level`，整数 0..9，缺失或非法旧值迁移到 0。
- `base_equipment_attributes`，保存未强化的稳定基础属性。

失败规则由独立 helper 实现：

- 当前 +0、+1、+2：失败后等级不变。
- 当前 +3、+4、+5：失败后等级为 +3。
- 当前 +6、+7、+8：失败后等级为 +6。
- 当前 +9：拒绝继续强化。

成功时等级加 1，最高 +9。成功和失败都消耗本次选择的强化石数量。

## 武器属性重算与战斗生效

武器使用 1008 已有 `equipment_attributes` 第一项作为本地主要攻击属性，不向 1008 追加字段。保存的 `base_equipment_attributes` 始终保持不变，有效属性每次由基础值和当前等级重新计算。

本地兼容武器攻击奖励表：

`(0, 1, 2, 3, 5, 7, 10, 14, 19, 25)`

即 `effective_attack = base_attack + bonus[strengthen_level]`。这不是旧官方数值公式；表集中定义以便后续替换。重复重算同一级别必须得到相同结果，不允许在当前有效值上连续乘算。

`combat_stats(role).physical_attack` 将计入当前已装备槽 10 武器的有效第一属性。因此强化背包武器只更新该物品；装备后，下一场战斗会实际使用强化后的攻击值。

由于尚未锁定 APK 的专用强化等级字段，本轮不改变 1008 布局，也不写 template ID。强化等级通过以下已确认文本字段显示：

- 强化等级大于 0 时，1008 名称显示为 `物品名 +N`，持久化基础名称不变。
- action 75 文本显示武器名、当前强化等级和主要攻击属性。
- 1009/82 与 1032 的现有说明文本附加强化等级和当前主要属性。

## action 处理与验证

action 97 返回页面引导文本。

action 75 只接受属于当前角色、属于背包或已装备容器、由 `is_equipment()` 识别且 `item_slot()==10` 的武器；返回单一字符串字段，不增加协议字段。

action 77 验证强化石属于当前角色、位于 bag、模板处于 APK 范围且有本地定义、数量大于 0。合法时不回 action 77，避免 APK `bw.n()` 清空两个选择槽；非法时返回 0 清除强化石槽。

action 74 重新验证武器和强化石，按当前强化等级返回每颗概率和说明文本。

action 92 在任何修改前重新验证：

- 装备实例存在且属于当前角色
- 是客户端装备类型、槽位为 10、位置为 bag 或 equipped
- 强化石实例存在、属于当前角色并位于 bag
- 强化石模板在 APK 接受范围且存在本地定义
- `1 <= count <= 5`
- `stone.quantity >= count`
- `strengthen_level < 9`

任一验证失败时不消耗物品、不改变等级，发送现有顶部提示以及 action 78 释放和重置客户端面板。

## 强化事务与帧顺序

验证完成后：

1. 计算每颗和总成功率并进行一次随机判定。
2. 成功则等级加 1；失败则应用独立降级规则。
3. 从基础属性重新计算有效武器属性。
4. 扣除强化石数量。
5. 保存 `data/roles.json`。
6. 发送武器 `item_frame(operation=3)`。
7. 强化石仍有剩余时发送其 `item_frame(operation=3)`；数量为 0 时先生成数量 0 的现有更新帧，再复用已验证的 `1009 [short(3), int(stone_id)]` 删除动作并从角色 items 删除。
8. 可选发送现有 `1049/action=4` 顶部提示，说明成功或失败及最终等级。
9. 最后发送 `1009 [short(78)]` 重置强化面板。

action 78 始终为该请求最后一个 1009 强化状态帧。不会发送 1009/action 92。
