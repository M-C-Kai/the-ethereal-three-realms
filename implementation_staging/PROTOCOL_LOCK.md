# 协议锁定记录

更新时间：2026-09-02

这份记录是当前 APK 已验证的协议基线。没有新的 smali/JAR 证据和真实客户端测试，不得凭猜测修改字段类型、操作码或角色资源。

## 门派技能学习协议

门派技能页使用 `1103`。APK `pmsj/work/e/dw.c()` 在打开页面时发送
`[byte(6)]` 请求目录；选择技能进入详情时，`pmsj/work/e/dy.a(w,int)` 发送
`[byte(2), int(skill_id), byte(current_level), byte(need_current_text), byte(need_next_text)]`，
随后把全局等待标志置为 true。服务端的详情响应必须仍为 `1103/action=2`，字段固定为：

`[byte(2), int(skill_id), int(current_level), int(required_role_level), int(silver_cost), int(exp_cost), int(first_prerequisite_level), int(second_prerequisite_level), string(effect), string(current_text), string(next_text), int(required_item_id), string(required_item_name), int(required_item_count)]`

其中客户端 `dy.a(main/w)` 会把前三项作为动作、技能号和当前等级，再按顺序读取
5 个整数条件、3 个字符串，再读取物品条件
`[int(required_item_id), string(required_item_name), int(required_item_count)]`。
因此响应总计 14 个字段；即使不需要物品也必须补齐 `[0, "", 0]`，否则未满级技能会越界读取。
缺少响应会使“请稍后”永久保留；数值字段不能缩成 byte。

在详情页确认学习/升级后，`dy.c_(0)` 发送
`[byte(3), int(skill_id)]`。本地测试闭环将角色的 `skill_levels["10001"]`
加一并保存，然后依次返回 `1103/action=0` 更新门派技能记录、`1103/action=5`
触发门派页重绘、`1132/action=0` 同步人物技能容器。无效或过期技能号返回
`1103([byte(3)])`；该动作在 APK 分发器中是安全空操作，同时会清除全局等待标志。

## 货币属性

APK 中可作为通用余额消费和交易的货币共三种。`1006` 人物属性表的对应关系为：

| 货币 | 人物属性 | APK 证据 |
|---|---:|---|
| 仙石 | 49 | `pmsj/work/e/dh.smali` 人物状态页；`pmsj/work/e/dp.smali` 仙石商店 |
| 银两 | 50 | `pmsj/work/b/ab.j()`；背包、交易和仓库界面 |
| 仙晶 | 52 | `pmsj/work/b/ab.i()`；兑换、商城和人物状态页 |

体力值、活力值、神炼值和斗胜值是人物状态资源，曜灵石是物品，均不并入通用货币。
角色存档使用独立的 `currencies` 字典持久化三种余额；新角色每种初始化为
`10_000_000`，旧存档只补充缺少的币种并保留已有余额。登录时三项均按 APK
要求使用 int 字段写入 `1006`，不改动其他人物属性。有效余额范围为
`0..2_147_483_647`；旧档中的非整数、布尔值、负数或越界值会安全修复为
`10_000_000` 并落盘，避免无效数据阻断角色登录。

## 物品协议

### 背包容量

`1006` 人物属性表中，属性 `62` 是个人背包容量。APK
`pmsj/work/b/ab.smali` 的 `g()I` 固定读取 `0x3e`，背包集合
`pmsj/work/b/a.smali` 的当前物品数会与该值比较。服务端为新角色初始化
`bag_capacity=40`，旧存档缺少该字段时只补入 `40` 并保留原有道具和角色资料；
登录时把持久化值写入 `1006/property 62`。

属性 `59` 是独立的仓库容量（`pmsj/work/b/ab.n()I` 读取 `0x3b`），不属于
本轮背包实现。仓库入口和 `1009` 存取动作暂不启用，不能把属性 59 与 62
合并或互换。

背包格位按物品实例计数，堆叠数量不额外占格。背包已有 40 个实例时，服务端
不得把已装备物品移回背包，也不得创建新的掉落实例；已有堆叠仍可正常增加数量。

`1008` 是完整物品实例记录，字段顺序和类型不能调整：

| 字段 | 类型 | 含义 |
|---:|---|---|
| 0 | byte | 操作码；当前装备/卸下必须使用 `3` |
| 1 | int | 物品实例 ID |
| 2/3 | short | 当前数量/最大数量 |
| 4 | byte | 位置：装备槽 `1..14`，背包 `50`，仓库 `51` |
| 5/6 | int | 状态标志/价格 |
| 7 | int | 模板 ID |
| 8 | string | 名称 |
| 9/10 | short | 物品标志/操作标志 |
| 11 | byte | 使用等级 |
| 12 | short | 图标编号，不是品质 |
| 13 | int | 到期时间 |
| 14/15 | short | 分组/排序 |

装备附加属性紧跟在字段 15 后面。

`1009` 动作：

- `82`：查看说明
- `3`：丢弃
- `4`：使用
- `5`：装备
- `6`：卸下

### 武器强化原生闭环

强化继续复用 APK 原生 `1009`，不新增消息号，也不扩展 `1008` 装备记录。C→S
动作固定为：`[short(97)]` 打开强化页，`[short(75), int(equipment_id)]` 选择装备，
`[short(77), int(equipment_id), int(stone_id)]` 选择强化石，随后用
`[short(74), int(equipment_id), int(stone_id)]` 查询单颗概率，最后以
`[short(92), int(equipment_id), int(stone_id), byte(count)]` 执行强化。S→C 使用
`97/75/77/74/78`，其中 `78` 清空选择并刷新强化页。
服务端绝不能回发 `1009/action=92`。

已确认的帧形状为：

- 打开：`[short(97), string(prompt)]`
- 装备选择：`[short(75), string(summary)]`
- 概率：`[short(74), short(rate_10000), string(summary)]`
- action 77 是清槽指令，不是有效选择确认：`[short(77), byte(0)]` 清强化石槽，
  `[short(77), byte(1), byte(1)]` 会调用 APK `bw.n()` 清空武器、强化石和数量槽。
  因此有效强化石的 C→S action 77 不单独回帧，由客户端紧接着发送的 action 74
  概率响应完成等待；仅无效材料回 `[short(77), byte(0)]`。
- 重置：`[short(78)]`

只有当前角色拥有、位于背包或装备槽 `10` 的武器可强化；强化石必须位于背包，
每次投入 `1..5` 颗且不能超过持有数量。两种本地映射模板为
`322260000/初级强化石` 和 `322261000/中级强化石`，均处于 APK 接受的
`322260000..322261002` 区间；它们与官方服务器道具定义的对应关系尚未确认。
新角色和首次迁移的旧角色各发放 1000 颗，使用持久化初始化标记保证只发一次。
强化石的 1008 `item_flags` 必须包含 `0x40`：APK `j.n()` 只在该位存在时把物品
视为堆叠物品，`bw.r()` 才会读取 quantity；缺少该位会把整组强化石误算为 1 颗。

初级强化石在 `+0..+8` 的单颗成功率（万分比）为
`2000,1800,1600,1400,1200,1000,800,600,400`；中级为
`2500,2200,2000,1800,1600,1400,1200,900,600`。所有单颗概率均不超过
2500，使 APK 按 `min(5, floor(10000/rate)+1)` 保持 1～5 颗选择；界面总概率和
服务端实际判定均按颗数线性相加并封顶 100%，这是强 UI 证据推断，
不是已确认的官方公式。失败时 `+0..+2` 保持原级，`+3..+5` 回到 `+3`，
`+6..+8` 回到 `+6`，`+9` 已封顶且不能继续执行。

强化等级 `strengthen_level`、未强化基础属性 `base_equipment_attributes` 和有效属性
`equipment_attributes` 均写入角色存档；保存失败时服务端必须回滚本次内存变更，不能
留下只在内存中扣石或降级的半事务。客户端通过名称后缀、说明文本
以及原有 1008 四个 short 装备属性看到结果，装备字段总数仍为 35。只有实际装备在
槽位 10 的武器，其有效第一属性才计入战斗物理攻击。APK 帮助已确认强化可能生成
幸运孔，但孔位字段和概率尚未锁定，本轮不实现。

动作 `3/4/5` 只接受 `1008` 位置 `50` 的背包物品，动作 `6` 只接受已装备位置。
物品实例必须能从当前角色的持久化物品列表中找到；仓库位置 `51` 不能通过这些
背包动作绕过容器边界。

装备/卸下的响应顺序为 `1008(operation=3)`、`1009([5])` 或 `1009([6])`，不能改成 operation=2。operation=2 会破坏客户端的装备操作菜单。

对于没有独立角色精灵图层的腰带、项链、戒指、外套、饰品、法宝，
`1008(operation=3)` 后还要发送一个不改变外观值的 `1017` 刷新帧；原 APK
通过该角色更新回调重绘已打开的人物装备页。该刷新帧不替代 1008，也不改变
属性 7、14～20 的有效值。

装备槽位固定为：

`1头盔、2肩甲、3铠甲、4腰带、5腿甲、6项链、7披风、8护腕、9鞋子、10武器、11戒指、12外套、13饰品、14法宝`。

## 人物外观协议

`1017` 格式固定为：

`[byte(0), int(role_id), int(pair_count), byte(property), int(value), ...]`

APK 数值类型标记中 `Long=9`，类型 `1` 实际按 Short 读取。完整 `1006` 的经验
属性 31/32 必须直接使用类型 9。增量 `1017` 则必须同时发送 `31/32` 的低
32 位，以及 `85/86` 的高 32 位；APK `main/e.O` 收到 85/86 后会分别重组为
Long 属性 31/32。

当前已确认的外观属性：

| 属性 | 图层 |
|---:|---|
| 7 | 武器；`270001` 由 APK 解析为武器图集 `27000` 加品质层 `30601` |
| 14 | 腿甲/裤腿 |
| 15 | 铠甲/胸部 |
| 16 | 肩甲 |
| 17 | 护腕 |
| 18 | 鞋子 |
| 19 | 披风 |
| 20 | 头盔 |

卸下时上述属性回到 `0`；属性 14 的零值由客户端解析为基础裤装。属性 22 是坐骑/变身，属性 26 是额外特效，不能当普通装备图层使用。

## 坐骑验证协议

坐骑不占用 `1008` 的 14 个普通装备槽，但 APK 另有独立的“坐骑”装备槽，位置字节为
`17`（反编译人物面板资源 `0x4661`）。验证令在背包位置 `50` 时发送
`1009([5, item_id])`，返回 `1008(operation=3, position=17)`、`1009([5])`，随后发送
`1017` 更新属性 `22=41004`；卸下时发送 `1009([6, item_id])`，返回位置 `50`、
`1009([6])`，随后更新为 `22=0`。属性 22 的更新会触发人物页面立即刷新，骑乘/下坐骑
状态同时写入角色存档。

原 APK 已经包含武器位和武器帧记录，但 `assets/res/role/100000.dat` 的六个待机方向组没有引用这些记录。
本地 APK 构建通过 `tools/patch_battle_weapon.py` 固定补入已由历史真机版本验证的待机武器组合；脚本只接受补丁前
`BD51B92A…` 或补丁后 `DEAE5D71…` 两个资源哈希并校验完整输出，不得凭感觉修改其他动作组或图层顺序。

## 修改门槛

任何协议改动必须同时满足：

1. 能在完整反编译目录或 JAR 中找到对应字段/分支证据；
2. 更新 `tests/` 单元测试；
3. 使用 `test_client.py` 做真实 TCP 装备、卸下和外观回滚测试；
4. 先验证再重启 6805 服务；
5. 角色存档字段新增必须提供向后兼容迁移；不得删除、重建或覆盖既有道具状态。

## 最小队伍创建与解散闭环

队伍协议是 `1023 (0x3ff)`，不是旧审计误标的 `1056 (0x420)`。未组队页的“创建队伍”按钮发送
`1023([short(0), int(role_id)])`；本地服先用 `1017` 将人物属性 0 的队长位 `0x40` 置上，再用
`1026/action=0` 下发一个队长成员记录：
`[byte(0), byte(1), string(name), int(role_id), int(max_hp), int(current_hp), byte(sect_id), int(level), int(current_mp), int(max_mp), int(flags)]`。
客户端把字段 2 起的九项保存为队伍成员，并以第一项成员为队长。

队长确认“解散队伍”发送 `1023([short(11)])`；服务端先通过 `1017` 清除属性 0 的队伍位，再回送相同的 short 动作。
即使连接内队伍状态已经清除，重复的 `1023/11` 也必须返回同一组清状态帧和确认帧，让残留的原生队长页面能够退出。
APK 的 `main/e.ag()` 收到 action 11 后清空队伍成员并关闭队伍界面。队伍状态只属于当前游戏连接，
不写入角色存档；邀请、申请、踢人、移交队长和多人同步不属于该最小闭环。

## 最小跨地图传送闭环

地图对象使用 APK 已确认的 `1126` 通用地图实体格式：
`[byte(0), byte(count), int(object_id), int(x), int(y), int(raw_model), string(name)]`。
smali 已确认一条实体交互路径发送 `2031([int(object_id), int(0), short(x), short(y), short(6), short(0)])`；
本次手机实测构建实际发送的是 `1010([short(7), int(object_id)])`，服务端同时保留两条路径。
本地服在 58 号“长安”下发 `580001/(55,55)` 和 `580003/(34,7)` 两个对象；收到任一对象的动作后，按当前地图注册表查询传送点，把角色存档的
`map_id/map_name/map_x/map_y` 切换到 `50000/传送测试区/8/6`，只发送 `1110` 世界描述；客户端随后按原流程
自行请求 `1010/12` 和 `1010/13`。目标地图使用项目内生成并验证的 `maps/50000.map.o`（90×90 草地、全可行走），`1010/13` 使用
APK 修复版内将 `58.map.ref/.map.o` 以 `50000.map.ref/.map.o` 别名随包提供，因此目标地图仍使用
原 APK 的本地图层解析和过渡动画；`1010/13` 保持 `status=0`。该闭环不改 1010/1407 的既有字段顺序。
50000 号地图出生点 `(8,6)` 旁另下发返回实体 `580002`（坐标 `(9,6)`）；触发后按同一流程
回到 `58/长安` 的 `(60,67)`，因此两个前向入口都具有完整返回闭环。传送点 ID 全局唯一，其他地图的对象 ID 不得在当前地图生效。妖兽对象收到任一交互包后会记录对象 ID、坐标和动作，并依次返回 APK 已确认的
`1040([byte(0)])` 战斗重置、双方 `1048` 参与者和 `1040/action=1`。普通攻击只能使用一条带 type-22 扣血效果的 type-1 `1042`；禁止拆成移动包、`1048` 刷新和 type-8 动作。动作批次后的完整 `1040/action=2` 用于启动客户端播放；客户端队列清空后回传的短格式 `1040/action=2` 是唯一回合完成屏障。

地图运行配置只以 `config.json/default_map_id + maps` 注册表为权威。每张地图独立声明名称、`.map.o`、引用策略、fallback 尺寸、出生点、妖兽、NPC 和传送点；未知地图不得继承 58 的任何字段。启动时必须校验地图键、尺寸、出生/实体/落点坐标、全局传送点 ID 和目标地图。旧扁平配置仅由兼容加载器迁移，不能再作为新配置示例。

战斗胜利结算顺序固定为 `1040/action=4`、`1010/action=18`、`1017`、`1008`、`1123`、`1049/action=3`。地图实体移除不是独立协议 18；它是 `1010` 的动作 18，字段布局为 `[int(monster_id), short(0), short(0), int(0), int(0), short(18)]`。通用 `1126` 实体 id 必须不小于 `1_000_000`，否则客户端不会从通用实体容器中删除它。结算只用 `1017` 增量更新人物属性 11/31/32（等级/当前经验/升级经验），不得发送登录初始化 `1006`，因为 `main/e.N` 收到 `1006` 会重建人物并主动发送 `1010/action=14` 重新进入地图。`1123` 仅写入公告缓存；可见结算使用 `1049/action=3`，字段为 `[byte(3), int(经验), int(宠物经验), int(银两), int(修为), string(物品数量标记)]`。APK 的 `main/e` 将其交给地图主界面内嵌的 `e/bs` 顶部奖励层，该层从顶部滑入、3 秒后滑出；禁止再用会打开居中 `br` 提示框的 `1512`。

NPC 必须使用 APK 原生 `2030`/`pmsj/work/b/t` 生成，不得伪装成 `1126` 通用实体。`2030` 字段为 `[int(id), int(x), int(y), int(dat_id), int(direction), int(0), string(name), int(flags), string(label)]`；`flags & 2` 必须为 0，使 NPC 进入 `b/m.V` 容器。地图点击会直接将该 `b/t` 设为当前目标，由 `b/n` 绘制内置 `0x203230` 脚下选中光圈，然后客户端发送 `2031([int(id), int(0), short(x), short(y), short(0), short(0)])`。

客户端每次上报 `1005` 移动路径后，`b/ab.am()` 会调用 `b/m.n(final_x, final_y)`，主动删除与最终坐标任一轴距离超过 20 格的 `V/W` NPC。服务端必须解码 `1005` 的起点、步数和 0..8 方向序列，在 NPC 重新进入 20 格区域时再次下发 `2030`。不得每步重发已在区域内的 NPC，因为 `b/m.a(Vector,n)` 会替换同 ID 对象并清除当前选中。

NPC 对话使用 `2032` 打开 screen 6（`pmsj/work/e/cb` / `6.ui`）的地图内紧凑半透明面板，而不是 `1533`/`dt` 的 300×335 大面板。帧头为 `[int(npc_id), byte(record_count)]`，每条记录固定 8 个字段；类型位于记录字段 5。类型 1 的字段 6 是正文，类型 2 的字段 4/6/7 是选项 id/文字/图标类型，最后用类型 100 记录解析 `b/m.V` 中的 NPC 标题和立绘并完成布局。选项点击回传 `2032([byte(option_id), byte(101), string(input)])`，客户端本地关闭面板，但同时开启全局等待标志；服务端必须回送无副作用的 `1010/action=7` 完整帧清除“请稍后”。

昆仑导师在 `2032` 中使用 option id `1` 表示“学习门派技能”。服务端只在连接内活动 NPC 仍属于当前地图、其配置为 `service=sect_skill_mentor/sect_id=1` 且角色门派也为 1 时，先回送 `1010/action=7`，再发送 `[int(0), short(0), short(0), int(1), int(179), short(69)]`。`main/e` 从字段 4 读取外部 screen `179/0xb3` 并映射为门派技能页 `602/0x25a`，从字段 3 读取 mode `1` 传给页面；其他选项或过期对话只能 ACK，不得打开学习页或改变技能。

本地昆仑 `60001` 必须在修复版 APK 中同时打包 `60001.map.ref/.map.o`，并配置 `map_ref_available=true`，使 `1010/action=13` 的 status 为 0。`1407` 负责逻辑地图、阻挡和镜像数据，但不能替代客户端渲染器所需的 `.map.ref` 复合图块引用。

等级系统的本地上限为 99，升级经验为 `当前等级×100`。默认自动升级；人物面板切换模式时客户端发送 `1010([short(36), int(0=自动/1=手动)])`，服务端按角色持久化。手动点击升级发送 `1129([short(3)])`；成功后服务端先用 `1017` 刷新等级、经验、生命/法力和基础属性，再下发含 12 个 int 的 `1129` 响应。`main/e.ar` 会播放人物升级特效，并用字段 3–11 绘制顶部“恭喜升级”成长列表。自动升级的击杀结算以该 `1129` 升级层取代普通 `1049/action=3`，避免两个顶部层在同一帧互相覆盖。

## 战斗逃跑协议

**方向必须分清**：C→S 的逃跑请求与 S→C 的逃跑结果都出现在 `1041`，但命令字不同，不能因为两个方向都出现 `10` 而混淆。

**C→S（玩家逃跑请求）= 命令 `6`。** 由 APK 的 逃跑 菜单分支 `E(6)` 写出（`pmsj.work.e.j` 逃跑分支 → `h.a`）：

| 字段 | 类型 | 含义 |
|---:|---|---|
| 0 | int | 命令字：`6`=逃跑 |
| 1 | byte | 当前回合 |
| 2 | int | 我方 actor id（`u()`） |
| 3 | int | 我方阵营 `f(7)`（玩家为 `1`） |
| 4..7 | int | 恒为 `0` |

真机实测：`[6, 1, 10003, 1, 0, 0, 0, 0]`。逃跑确认对话框 `确定要逃跑吗?` 走 `c_(0)`，最终同样发命令 `6`。

**C→S 命令 `10` 不是玩家逃跑**，而是 **退出观战**（`pmsj.work.b.h.b(II)`，调用方 `pmsj.work.e.j.c_(1)`，对应确认框 `确定要退出观战吗?`）。本地单人战斗无观战模式，该命令不得走玩家逃跑分支。

**S→C（逃跑结果）由 APK 入站 `main/e.V` 处理`：命令字 `10` 且字段 1 等于本地玩家 id 时，本地 APK 调用 `e.j.escapeStart()`。因此服务端对玩家逃跑的成功响应为 `1041([int(10), int(player_id)])`，两个字段都为 int（`La/c/m`）。服务端为 C→S 命令 `6` 识别为逃跑请求，再用 `battle_escape_frame(player_id)` 立即回 `[10, player_id]` 开始退场。

### 1041 C→S 命令字典（APK 已确认，字段 0）
| 命令 | 含义 | 生产者 |
|---:|---|---|
| 1 | 攻击 | `h.a` p1=1 |
| 2 | 防御 | `E(2)` |
| 6 | 逃跑 | `E(6)` / `c_(0)` |
| 8 | 召回 | `b(8, …)` |
| 10 | 退出观战 | `h.b` / `c_(1)` |
| 12 | 待机 | `E(0xc)` |

命令 `3/4/5` 无可靠 APK 证据，不猜测。

逃跑分支与胜利结算完全独立：服务端在第一个 C→S `1041/6` 到达时立即结束服务端战斗状态，并只回送一条 S→C `1041([10, player_id])`。不发送逃跑用 `1042`、不等待 `1040/action=2` ACK、不发送 `1040/action=4`、不发送 `1010/action=18`（地图实体移除）、不结算奖励（`1008/1017/1123/1049`）。妖兽保留在地图上。逃跑不扣血量、不触发反击、不推进回合。

### 本地逃跑退场表现
本地 APK 的 `main/e.V` 收到 `[10, player_id]` 后调用 `e.j.escapeStart()`：它使用 fighter 的 `escapeMove()` 向屏外移动，由 `escapeDone()` 驱动战斗页关闭和 `main/b.c()` 清理。退场时长为 **500 ms**。

玩家点击指令时，`b(IIIII)` 会把 fighter 的 `K` 标志置为 true，使回合准备计时器 `W` 把沙漏切换成“准备完成”图标。普通动作的 `i()` 会调用 `W.g()` 隐藏整组状态图标；逃跑绕过了 `i()`，因此 `escapeStart()` 同样必须调用 `W.g()`，并用 `fighter.a(false)` 清理已完成指令标志。这会让沙漏/“准备完成”在逃跑响应到达时立即消失，不等退场完成。战场 **fighter 离场**的另一条结果命令 `101`（`0x65`）仍不用于玩家逃跑。

### 逃跑后防重复触发（escape encounter guard）
逃跑成功后会话内记录 `{map_id, monster_id, player_id, origin=玩家最后已知坐标}`。**guard 建立不依赖接触 tile**：真机开战走 `1010([short(7), int(object_id)])`（无接触 tile），故一律按 `(map_id, monster_id)` 抑制同一地图、同一怪物在逃跑瞬间的再次触发（`BATTLE_ESCAPE_RETRIGGER_SUPPRESSED`），不重新开战、不锁怪物。被抑制的请求不能静默丢弃：`b/ab.aj()` 在发送 `1010/7` 前把全局等待标志置为 true，而 S→C `1010` 分发入口会先清除这两个标志。因此服务端返回完整的无副作用确认 `[int(object_id), short(0), short(0), int(0), int(0), short(7)]`；action 7 不在 S→C 1010 动作表中，不会执行地图动作，但能消除“请稍后”。`origin` 取 `player_tile`（由 `1005` 或携带 tile 的 `2031` 更新），可空（未知位置也不会漏建 guard）。

解除时机（绑定真实移动，`BATTLE_ESCAPE_GUARD_CLEARED`）：
- 玩家移动协议 `1005`（`b/ab.am`，首两个字段是当前 `(x,y)` 两 short）到达且坐标 ≠ 逃跑 `origin` → 清除 guard，日志带 `old_tile=/new_tile=`。重复上报同一坐标不解除。
- 若建立时 `origin` 为空，第一个 `1005` 仅建立参照格（`BATTLE_ESCAPE_GUARD_ORIGIN_ESTABLISHED`）不解除；随后移动到异于该参照的格子才解除。
- 新战斗 `begin()` 或地图重载 `reset_encounter()` 也会清除 guard。

因此“战斗→逃跑→回地图→原地再点：禁止；走开→再走回→点击同一怪：可再战”成立；guard 只是防逃跑瞬间重复触发，不会永久免战，也不影响其它怪物（不同 monster/map 均不抑制）。

本地服对逃跑采取“必定成功”的服务端策略（原始服务器有概率判定，属本地覆盖策略，与 APK 确认的协议无关，且仅影响单机本地服）。


## 地图/战斗武器外观统一

APK `pmsj/work/b/v.r()` 明确执行 `property 7 -> v.e(I)`，而 `property 22 -> v.G(I)`。旧审计把 `H/I/G` 的 `40000` 路径归到 property7 是误判。

`v.e(I)` 的地图武器编码规则为：`property7 / 10 = weapon image`、`property7 % 10 = quality`；品质非 0 时用 `property7 / 1000` 匹配固定 family 数组 `[241,220,290,231,280,250,270,271,242,240,260,221,230]`，品质覆盖 image 为 `30000 + family_index*100 + quality`。这与战斗 `1048 field[2]` 使用的完整武器编码一致。

当前用户按 APK contact sheet 确认的 icon group→family 映射为：`21→220, 22→260, 23→271, 24→250, 25→231, 26→280, 27→242, 28→240, 29→241, 30→221, 31→290, 32→270, 33→230`。族 271 映射 `27101..27110`；族 231 只使用 `23100..23109`，额外 `23110/23111` 不自动分配。

同一已装备武器必须满足：`character_appearance(role)[7] == 1048 field[2] == battle_weapon_field2_from_icon(icon_code, quality)`；卸下武器后均为 `0`。
