# 协议锁定记录

更新时间：2026-08-25

这份记录是当前 APK 已验证的协议基线。没有新的 smali/JAR 证据和真实客户端测试，不得凭猜测修改字段类型、操作码或角色资源。

## 物品协议

`1008` 是完整物品实例记录，字段顺序和类型不能调整：

| 字段 | 类型 | 含义 |
|---:|---|---|
| 0 | byte | 操作码；当前装备/卸下必须使用 `3` |
| 1 | int | 物品实例 ID |
| 2/3 | short | 当前数量/最大数量 |
| 4 | byte | 位置：装备槽 `1..14`，背包 `50`，仓库 `51` |
| 5/6 | int | 状态标志/价格 |
| 7 | int | 模板 ID |
| 8 | string | 名称 |
| 9/10 | short | 物品标志/操作标志 |
| 11 | byte | 使用等级 |
| 12 | short | 图标编号，不是品质 |
| 13 | int | 到期时间 |
| 14/15 | short | 分组/排序 |

装备附加属性紧跟在字段 15 后面。

`1009` 动作：

- `82`：查看说明
- `3`：丢弃
- `4`：使用
- `5`：装备
- `6`：卸下

装备/卸下的响应顺序为 `1008(operation=3)`、`1009([5])` 或 `1009([6])`，不能改成 operation=2。operation=2 会破坏客户端的装备操作菜单。

对于没有独立角色精灵图层的腰带、项链、戒指、外套、饰品、法宝，
`1008(operation=3)` 后还要发送一个不改变外观值的 `1017` 刷新帧；原 APK
通过该角色更新回调重绘已打开的人物装备页。该刷新帧不替代 1008，也不改变
属性 7、14～20 的有效值。

装备槽位固定为：

`1头盔、2肩甲、3铠甲、4腰带、5腿甲、6项链、7披风、8护腕、9鞋子、10武器、11戒指、12外套、13饰品、14法宝`。

## 人物外观协议

`1017` 格式固定为：

`[byte(0), int(role_id), int(pair_count), byte(property), int(value), ...]`

APK 数值类型标记中 `Long=9`，类型 `1` 实际按 Short 读取。完整 `1006` 的经验
属性 31/32 必须直接使用类型 9。增量 `1017` 则必须同时发送 `31/32` 的低
32 位，以及 `85/86` 的高 32 位；APK `main/e.O` 收到 85/86 后会分别重组为
Long 属性 31/32。

当前已确认的外观属性：

| 属性 | 图层 |
|---:|---|
| 7 | 武器；`270001` 由 APK 解析为武器图集 `27000` 加品质层 `30601` |
| 14 | 腿甲/裤腿 |
| 15 | 铠甲/胸部 |
| 16 | 肩甲 |
| 17 | 护腕 |
| 18 | 鞋子 |
| 19 | 披风 |
| 20 | 头盔 |

卸下时上述属性回到 `0`；属性 14 的零值由客户端解析为基础裤装。属性 22 是坐骑/变身，属性 26 是额外特效，不能当普通装备图层使用。

## 坐骑验证协议

坐骑不占用 `1008` 的 14 个普通装备槽，但 APK 另有独立的“坐骑”装备槽，位置字节为
`17`（反编译人物面板资源 `0x4661`）。验证令在背包位置 `50` 时发送
`1009([5, item_id])`，返回 `1008(operation=3, position=17)`、`1009([5])`，随后发送
`1017` 更新属性 `22=41004`；卸下时发送 `1009([6, item_id])`，返回位置 `50`、
`1009([6])`，随后更新为 `22=0`。属性 22 的更新会触发人物页面立即刷新，骑乘/下坐骑
状态同时写入角色存档。

原 APK 已经包含武器位和武器帧记录，但 `assets/res/role/100000.dat` 的六个待机方向组没有引用这些记录。
本地 APK 构建通过 `tools/patch_battle_weapon.py` 固定补入已由历史真机版本验证的待机武器组合；脚本只接受补丁前
`BD51B92A…` 或补丁后 `DEAE5D71…` 两个资源哈希并校验完整输出，不得凭感觉修改其他动作组或图层顺序。

## 修改门槛

任何协议改动必须同时满足：

1. 能在完整反编译目录或 JAR 中找到对应字段/分支证据；
2. 更新 `tests/` 单元测试；
3. 使用 `test_client.py` 做真实 TCP 装备、卸下和外观回滚测试；
4. 先验证再重启 6805 服务；
5. 不改变 `data/roles.json` 的既有存档结构。

## 最小跨地图传送闭环

地图对象使用 APK 已确认的 `1126` 通用地图实体格式：
`[byte(0), byte(count), int(object_id), int(x), int(y), int(raw_model), string(name)]`。
smali 已确认一条实体交互路径发送 `2031([int(object_id), int(0), short(x), short(y), short(6), short(0)])`；
本次手机实测构建实际发送的是 `1010([short(7), int(object_id)])`，服务端同时保留两条路径。
本地服在 58 号地图下发对象 `580001`（坐标 `64,67`），收到该动作后把角色存档的
`map_id/map_name` 切换到 `50000/传送测试区`，只发送 `1110` 世界描述；客户端随后按原流程
自行请求 `1010/12` 和 `1010/13`。目标地图使用项目内生成并验证的 `maps/50000.map.o`（32×32 草地、全可行走），`1010/13` 使用
APK 修复版内将 `58.map.ref/.map.o` 以 `50000.map.ref/.map.o` 别名随包提供，因此目标地图仍使用
原 APK 的本地图层解析和过渡动画；`1010/13` 保持 `status=0`。该闭环不改 1010/1407 的既有字段顺序。
50000 号地图出生点 `(8,6)` 旁另下发返回实体 `580002`（坐标 `(9,6)`）；触发后按同一流程
回到 `58/仙石村` 的 `(63,67)`，因此该传送闭环现在是双向的。妖兽对象收到任一交互包后会记录对象 ID、坐标和动作，并依次返回 APK 已确认的
`1040([byte(0)])` 战斗重置、双方 `1048` 参与者和 `1040/action=1`。普通攻击只能使用一条带 type-22 扣血效果的 type-1 `1042`；禁止拆成移动包、`1048` 刷新和 type-8 动作。动作批次后的完整 `1040/action=2` 用于启动客户端播放；客户端队列清空后回传的短格式 `1040/action=2` 是唯一回合完成屏障。

战斗胜利结算顺序固定为 `1040/action=4`、`1010/action=18`、`1017`、`1008`、`1123`、`1049/action=3`。地图实体移除不是独立协议 18；它是 `1010` 的动作 18，字段布局为 `[int(monster_id), short(0), short(0), int(0), int(0), short(18)]`。通用 `1126` 实体 id 必须不小于 `1_000_000`，否则客户端不会从通用实体容器中删除它。结算只用 `1017` 增量更新人物属性 11/31/32（等级/当前经验/升级经验），不得发送登录初始化 `1006`，因为 `main/e.N` 收到 `1006` 会重建人物并主动发送 `1010/action=14` 重新进入地图。`1123` 仅写入公告缓存；可见结算使用 `1049/action=3`，字段为 `[byte(3), int(经验), int(宠物经验), int(银两), int(修为), string(物品数量标记)]`。APK 的 `main/e` 将其交给地图主界面内嵌的 `e/bs` 顶部奖励层，该层从顶部滑入、3 秒后滑出；禁止再用会打开居中 `br` 提示框的 `1512`。

NPC 必须使用 APK 原生 `2030`/`pmsj/work/b/t` 生成，不得伪装成 `1126` 通用实体。`2030` 字段为 `[int(id), int(x), int(y), int(dat_id), int(direction), int(0), string(name), int(flags), string(label)]`；`flags & 2` 必须为 0，使 NPC 进入 `b/m.V` 容器。地图点击会直接将该 `b/t` 设为当前目标，由 `b/n` 绘制内置 `0x203230` 脚下选中光圈，然后客户端发送 `2031([int(id), int(0), short(x), short(y), short(0), short(0)])`。

客户端每次上报 `1005` 移动路径后，`b/ab.am()` 会调用 `b/m.n(final_x, final_y)`，主动删除与最终坐标任一轴距离超过 20 格的 `V/W` NPC。服务端必须解码 `1005` 的起点、步数和 0..8 方向序列，在 NPC 重新进入 20 格区域时再次下发 `2030`。不得每步重发已在区域内的 NPC，因为 `b/m.a(Vector,n)` 会替换同 ID 对象并清除当前选中。

NPC 对话使用 `2032` 打开 screen 6（`pmsj/work/e/cb` / `6.ui`）的地图内紧凑半透明面板，而不是 `1533`/`dt` 的 300×335 大面板。帧头为 `[int(npc_id), byte(record_count)]`，每条记录固定 8 个字段；类型位于记录字段 5。类型 1 的字段 6 是正文，类型 2 的字段 4/6/7 是选项 id/文字/图标类型，最后用类型 100 记录解析 `b/m.V` 中的 NPC 标题和立绘并完成布局。选项点击回传 `2032([byte(option_id), byte(101), string(input)])`，客户端本地关闭面板，但同时开启全局等待标志；服务端必须回送无副作用的 `1010/action=7` 完整帧清除“请稍后”。

等级系统的本地上限为 99，升级经验为 `当前等级×100`。默认自动升级；人物面板切换模式时客户端发送 `1010([short(36), int(0=自动/1=手动)])`，服务端按角色持久化。手动点击升级发送 `1129([short(3)])`；成功后服务端先用 `1017` 刷新等级、经验、生命/法力和基础属性，再下发含 12 个 int 的 `1129` 响应。`main/e.ar` 会播放人物升级特效，并用字段 3–11 绘制顶部“恭喜升级”成长列表。自动升级的击杀结算以该 `1129` 升级层取代普通 `1049/action=3`，避免两个顶部层在同一帧互相覆盖。

## 战斗逃跑协议

**方向必须分清**：C→S 的逃跑请求与 S→C 的逃跑结果都出现在 `1041`，但命令字不同，不能因为两个方向都出现 `10` 而混淆。

**C→S（玩家逃跑请求）= 命令 `6`。** 由 APK 的 逃跑 菜单分支 `E(6)` 写出（`pmsj.work.e.j` 逃跑分支 → `h.a`）：

| 字段 | 类型 | 含义 |
|---:|---|---|
| 0 | int | 命令字：`6`=逃跑 |
| 1 | byte | 当前回合 |
| 2 | int | 我方 actor id（`u()`） |
| 3 | int | 我方阵营 `f(7)`（玩家为 `1`） |
| 4..7 | int | 恒为 `0` |

真机实测：`[6, 1, 10003, 1, 0, 0, 0, 0]`。逃跑确认对话框 `确定要逃跑吗?` 走 `c_(0)`，最终同样发命令 `6`。

**C→S 命令 `10` 不是玩家逃跑**，而是 **退出观战**（`pmsj.work.b.h.b(II)`，调用方 `pmsj.work.e.j.c_(1)`，对应确认框 `确定要退出观战吗?`）。本地单人战斗无观战模式，该命令不得走玩家逃跑分支。

**S→C（逃跑结果）由 APK 入站 `main/e.V` 处理`：命令字 `10` 且字段 1 等于本地玩家 id 时，本地 APK 调用 `e.j.escapeStart()`。因此服务端对玩家逃跑的成功响应为 `1041([int(10), int(player_id)])`，两个字段都为 int（`La/c/m`）。服务端为 C→S 命令 `6` 识别为逃跑请求，再用 `battle_escape_frame(player_id)` 立即回 `[10, player_id]` 开始退场。

### 1041 C→S 命令字典（APK 已确认，字段 0）
| 命令 | 含义 | 生产者 |
|---:|---|---|
| 1 | 攻击 | `h.a` p1=1 |
| 2 | 防御 | `E(2)` |
| 6 | 逃跑 | `E(6)` / `c_(0)` |
| 8 | 召回 | `b(8, …)` |
| 10 | 退出观战 | `h.b` / `c_(1)` |
| 12 | 待机 | `E(0xc)` |

命令 `3/4/5` 无可靠 APK 证据，不猜测。

逃跑分支与胜利结算完全独立：服务端在第一个 C→S `1041/6` 到达时立即结束服务端战斗状态，并只回送一条 S→C `1041([10, player_id])`。不发送逃跑用 `1042`、不等待 `1040/action=2` ACK、不发送 `1040/action=4`、不发送 `1010/action=18`（地图实体移除）、不结算奖励（`1008/1017/1123/1049`）。妖兽保留在地图上。逃跑不扣血量、不触发反击、不推进回合。

### 本地逃跑退场表现
本地 APK 的 `main/e.V` 收到 `[10, player_id]` 后调用 `e.j.escapeStart()`：它使用 fighter 的 `escapeMove()` 向屏外移动，由 `escapeDone()` 驱动战斗页关闭和 `main/b.c()` 清理。退场时长为 **500 ms**。

玩家点击指令时，`b(IIIII)` 会把 fighter 的 `K` 标志置为 true，使回合准备计时器 `W` 把沙漏切换成“准备完成”图标。普通动作的 `i()` 会调用 `W.g()` 隐藏整组状态图标；逃跑绕过了 `i()`，因此 `escapeStart()` 同样必须调用 `W.g()`，并用 `fighter.a(false)` 清理已完成指令标志。这会让沙漏/“准备完成”在逃跑响应到达时立即消失，不等退场完成。战场 **fighter 离场**的另一条结果命令 `101`（`0x65`）仍不用于玩家逃跑。

### 逃跑后防重复触发（escape encounter guard）
逃跑成功后会话内记录 `{map_id, monster_id, player_id, origin=玩家最后已知坐标}`。**guard 建立不依赖接触 tile**：真机开战走 `1010([short(7), int(object_id)])`（无接触 tile），故一律按 `(map_id, monster_id)` 抑制同一地图、同一怪物在逃跑瞬间的再次触发（`BATTLE_ESCAPE_RETRIGGER_SUPPRESSED`），不重新开战、不锁怪物。被抑制的请求不能静默丢弃：`b/ab.aj()` 在发送 `1010/7` 前把全局等待标志置为 true，而 S→C `1010` 分发入口会先清除这两个标志。因此服务端返回完整的无副作用确认 `[int(object_id), short(0), short(0), int(0), int(0), short(7)]`；action 7 不在 S→C 1010 动作表中，不会执行地图动作，但能消除“请稍后”。`origin` 取 `player_tile`（由 `1005` 或携带 tile 的 `2031` 更新），可空（未知位置也不会漏建 guard）。

解除时机（绑定真实移动，`BATTLE_ESCAPE_GUARD_CLEARED`）：
- 玩家移动协议 `1005`（`b/ab.am`，首两个字段是当前 `(x,y)` 两 short）到达且坐标 ≠ 逃跑 `origin` → 清除 guard，日志带 `old_tile=/new_tile=`。重复上报同一坐标不解除。
- 若建立时 `origin` 为空，第一个 `1005` 仅建立参照格（`BATTLE_ESCAPE_GUARD_ORIGIN_ESTABLISHED`）不解除；随后移动到异于该参照的格子才解除。
- 新战斗 `begin()` 或地图重载 `reset_encounter()` 也会清除 guard。

因此“战斗→逃跑→回地图→原地再点：禁止；走开→再走回→点击同一怪：可再战”成立；guard 只是防逃跑瞬间重复触发，不会永久免战，也不影响其它怪物（不同 monster/map 均不抑制）。

本地服对逃跑采取“必定成功”的服务端策略（原始服务器有概率判定，属本地覆盖策略，与 APK 确认的协议无关，且仅影响单机本地服）。
