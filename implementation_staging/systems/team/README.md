# 组队状态与客户端同步

`TeamRegistry` 是唯一队伍状态源：`member_to_leader` 保证一名玩家只能属于一支队伍；`teams` 保存队长、成员顺序和暂离集合；邀请与入队申请是带 60 秒有效期的临时状态。队伍状态只在进程内保存，断线、切换角色和服务重启后清理，不写入角色存档。

所有 `1023` 客户端请求由 `TeamSystem` 独占。创建队伍先登记队长；邀请确认必须匹配待处理邀请、在线角色和队伍容量，成功后一次性修改注册表，再向双方下发 `1026/0` 成员记录。离队、解散和断线先清理注册表，再向仍在线的成员发送移除或解散帧。这样“再次邀请提示已在队伍中”和“成员列表为空”不会来自两个互不相干的状态源。

原 APK 的 `1026/0` 接收分支在写入成员表后还会强制打开页面 `0x5c`，导致地图功能 UI 消失。`tools/patch_team_roster_ui.py` 只删除这次自动跳页，保留成员表更新；用 `build_team_apk.ps1` 生成并签名 `build_artifacts/apk/piaomiao_local_team.apk`。服务端的双人队伍同步需要使用这个新 APK。

跟随只在双方已进同一视野、队员未暂离时启用。入队后给全队每个客户端发送一次按接收方定制的 `1038` 链接；队长每次移动时，地图系统通过装配期注入的回调查询队伍状态，对跟随者发送 `1038` 代替普通 `1005`。帧内 id 语义来自 `b/m.o(I)`：本地玩家按 raw role id 命中、他人按 actor id（1_000_000+role_id）命中，因此链头（队长）与链表首位的自己（队员客户端）用 raw id，其余链员用 actor id。注意消息号是 **1038（0x40e → main/e.ai）**；1028（0x404）在 APK 主接收分发表中不存在，会被静默丢弃。APK 的普通 `1005` 分支调用 `v.ad()`，会清掉跟随链，因此不能只在入队时发送一次 `1028`。服务端仍以客户端随后上报的 `1005` 更新队员真实坐标；若客户端不产生该上报，需继续检查 APK 的本机角色跟随逻辑，不能凭服务端角色存档推断画面已移动。
